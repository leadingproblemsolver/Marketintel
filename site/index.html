Six ways n8n workflows fail without telling you

These are the failure categories the audit looks for. Each one can leave executions looking healthy while the business result is wrong or missing.

01

Continue-on-fail hides a real error

A node errors, but “continue on fail” lets the run finish green. Downstream steps may act on missing or partial data, and nothing records an incident.

02

Zero items treated as success

A source returns an empty list, or “always output data” turns no rows into one item. The run completes, but nothing was processed and nobody is alerted.

03

Alerting that is itself switched off

The error workflow is unlinked, inactive or misconfigured, so the failure notification never goes out. You assume silence means health.

04

Side effect before the state is saved

A message, charge or record is created, then persisting state fails. A retry repeats the side effect, such as a duplicate email or payment, unless an idempotency key prevents it.

05

Schedules that quietly stop

A workflow is deactivated or its trigger stalls. There is no failed execution to alert on because nothing ran. Only an independent heartbeat notices a missed run.

06

Error output wired to nothing

A node’s error branch exists but ends in a no-op. The failure is “handled” on the canvas and discarded in practice, with no structured failure record.
